## 详情

### 一、发现方式

不是读代码推测，是**在真实下游工程里实测**：

```
$ bash scripts/verify-downstream-consumption.sh --run
```

### 二、缺陷 1 · 解析兜底路径被记为 WARN（2 条/工具方法）

`SingleStarter` 三处兜底分支（描述 / 参数必填性 / 参数描述）在所有已配置解析器都未命中时打印：

```
WARN SingleStarter : Please note that the parsing module you specified resulted in the
                     com.example.demo.OrderController-getOrder tool not parsing the param required
```

**问题在语义**：这句话读起来像「你配错了解析器」，实际含义是「所有解析器都没给出答案，框架按设计回退默认值」——这是**常规路径**，不是错误。级别与措辞双重误导，把框架的正常兜底暴露成了用户需要处理的告警，且每个工具方法各刷一条。

同一批还有 `JavaDocDesParser` 的 `log.warn("...JavaDoc解析失败")`：jar 部署时 `.java` 源码不在 classpath 属**预期状态**（该解析器本身已 `@Deprecated`），同样按失败告警处理。

**修复**：三处 + 一处全部降为 `debug`，措辞改为如实描述行为（"未被任何已配置解析器命中，已回退默认 X"）。顺带把 `runParamDesParse` 的 `result == null` 判空统一为 `!StringUtils.hasText(result)`，与同文件另两条分支一致。

### 三、缺陷 2 · 内部配置类过早实例化（4 条/次启动）

```
WARN ConfigurationClassPostProcessor : Cannot enhance @Configuration bean definition
     'com.ai.plug.autoconfigure.McpConfig$CompleteSpecificationConfiguration'
     since its singleton instance has been created too early. ...
```

**根因链**（已逐段核实）：

1. `McpToolScanRegistrar`（`ImportBeanDefinitionRegistrar`）在**配置类解析阶段**直接 `beanFactory.getBean(IToolContext.class)`
2. `IToolContext` 的 bean 定义位于 `McpConfig$ToolSpecificationConfiguration` 这个 `@Configuration` 类中 → 该配置类被提前实例化
3. 此时 `ConfigurationClassPostProcessor` 正准备对该配置类做 CGLIB 增强，发现单例已在创建中 → **无法增强** → 打印警告并放弃增强
4. 同理波及 `Resource` / `Prompt` / `Complete` 三个 Specification 配置类

**修复**：`McpConfig` 的 5 个内部 `@Configuration` 类一律声明 `@Configuration(proxyBeanMethods = false)`。

**安全性论证**：内部各 `@Bean` 方法**零互调**（逐个核实，全部为无参工厂或依赖参数注入），因此关闭 CGLIB 代理语义对行为零影响 —— 这也是 Spring 官方提示里的首选方案。

### 四、为什么把「启动日志无噪声」断言放在脚本而非单测

第一版把日志断言写进了 `@SpringBootTest`（用 `ListAppender` 挂在 `ConfigurationClassPostProcessor` 的 logger 上），实测**恒真** —— Spring Boot 的 `LoggingApplicationListener` 会在 refresh 早期重建日志配置，把手工挂载的 appender 冲掉。

因此改为**双层门禁**：
- **结构断言**（单测，稳定可靠）：`McpConfig` 全部内部 `@Configuration` 类的 `proxyBeanMethods()` 必须为 `false`
- **行为断言**（端到端，真实用户视角）：`verify-downstream-consumption.sh` 断言下游启动日志中「配置类增强 / 解析兜底 / Javadoc 跳过」三类框架噪声告警计数必须为 0

## 发现

### F1 · 「进程内日志断言」在 Spring Boot 下不可靠 🔴 已换方案

`@SpringBootTest` + `ListAppender` 捕获框架启动期日志，断言**恒真**（因日志系统重置 appender）。教训：Spring Boot 项目的启动期行为断言，应落在**外部进程 + 真实日志文件**的视角上，而非同进程捕获。

### F2 · `McpToolScanRegistrar` 在配置类解析阶段 `getBean` 是反模式 🟡 未修，暂无风险

该写法（配置类解析期就实例化普通 bean）本身就是 Spring 反模式，会让该 bean 无法被常规后置处理器处理。当前靠 `proxyBeanMethods=false` 消除了可见症状，但根因仍在。

> 彻底修法（`RuntimeBeanReference` 延迟引用 / 把 `IToolContext` 定义移出 `@Configuration`）会改变 bean 初始化时序，**属协议层改动，须董事长批准**。当前无功能风险，故不动。

### F3 · `JavaDocDesParser` 已 `@Deprecated` 但仍在默认解析链中 🟡 未修

默认 des 链含 `JAVADOC`（`Conditions.ParserCondition` 的默认值），即该已废弃解析器**每个下游用户默认都会激活**。开发环境（源码在 classpath）它是有用的；jar 环境必然失败（现已降为 debug，不再刷屏）。

> 建议后续版本从默认链中移除 `JAVADOC`，或提供「仅在检测到源码可读时才启用」的条件。属默认值语义变更，须董事长批准。

### F4 · `WebMvcSseSyncServerTransportTests.java` 是全注释的死文件 🟢 未修

`server2mcp-core/src/test/java/com/ai/plug/core/WebMvcSseSyncServerTransportTests.java` 全文被注释，无任何可执行代码。属死代码，可删（但需按「破坏性删除多源验证」流程走 grep + LSP + 跨模块评估）。
