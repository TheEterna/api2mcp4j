## 一、缺口事实（代码实证，非文档转述）

### 1.1 解析器激活链路

`McpConfig`（autoconfigure 模块）用 13 处 `@ConditionalOnParser` 声明解析器 Bean：

| 链 | Bean 声明位置 | `@ConditionalOnParser` value |
|---|---|---|
| des（6） | `McpConfig.java:243/249/256/262/268/274` | MCPTOOL, TOOL, JACKSON, JAVADOC, SWAGGER3, SWAGGER2 |
| param（7） | `McpConfig.java:285/292/299/305/312/318/325` | MCPTOOL, TOOL, SPRINGMVC, JACKSON, JAVADOC, SWAGGER3, SWAGGER2 |

### 1.2 缺口现场

`Conditions.ParserCondition.matches()`（`server2mcp-autoconfigure/.../conditional/Conditions.java:62-95`）只做一件事：把**配置里写的名字**与**注解声明的名字**逐个 `equalsIgnoreCase` 比对。

```
plugin.mcp.parser.des: MCPTOOL, JAVADOC, TOOL, JACKSON, SWAGGER3, JAVADOCS   ← 拼错
                                   ↓
JAVADOCS ≠ 任何已声明 value → 该解析器静默不激活 → 启动零告警
                                   ↓
运行时才发现：工具描述缺失（回落到更低优先级的解析器）或参数 Schema 退化
```

**当前成熟度：🔴 静默缺失，运行时才暴雷** —— 注册纪律 §五 R2 的最低档。`来源：REGISTRATION_DISCIPLINE_SPEC.md §五 R2 成熟度分级表 + V-2 违规清单`

### 1.3 放大风险（本仓已实测到的痛点）

- 配置键是**单数** `param` / `des`（不是 `params` / `descriptions`），CLAUDE.md 本体曾因此写错被当场纠正 —— 键名本身就是易错点
- 大小写不敏感（`equalsIgnoreCase`）→ `McpTool` / `mcpTool` 都能过，但文档里写的是全大写，两套写法混用不易察觉
- 「全部拼错」场景下**一个解析器都不会激活**，而 `Conditions.ParserCondition` 因为没有被求值，**连 WARN 都不会打**

## 二、方案设计

### 2.1 核心思路：单一权威源 + 启动期断言 + 分级处置

| 层 | 措施 | 作用 |
|---|---|---|
| **L-a 单一权威源** | 新建 `ParserNames` 常量类，13 处 `@ConditionalOnParser(value = ...)` 改引用常量 | 消除「注解字面量」与「校验集合」两处定义的漂移隐患 |
| **L-b 启动期断言** | 新增 `ParserNameValidator`（`ApplicationRunner`），启动时比对配置值与已知名 | 覆盖「全部拼错」等 `ParserCondition` 不会被求值的极端场景 |
| **L-c 分级处置** | 默认 WARN（不阻断，向后兼容）；`plugin.mcp.parser.strict=true` 时抛异常拒绝启动 | 满足 R2 🟡 级要求，同时给严格用户 🟢 通道 |

### 2.2 已知名集合的构造

**不使用 classpath 扫描**（避免启动开销与扫描失败面），直接由 `ParserNames` 常量类持有两个 `Set`：

```java
public final class ParserNames {
    public static final String MCPTOOL = "MCPTOOL";
    public static final String TOOL     = "TOOL";
    public static final String JACKSON  = "JACKSON";
    public static final String JAVADOC  = "JAVADOC";
    public static final String SPRINGMVC = "SPRINGMVC";
    public static final String SWAGGER2 = "SWAGGER2";
    public static final String SWAGGER3 = "SWAGGER3";

    public static final Set<String> DES_NAMES   = Set.of(MCPTOOL, TOOL, JACKSON, JAVADOC, SWAGGER3, SWAGGER2);
    public static final Set<String> PARAM_NAMES = Set.of(MCPTOOL, TOOL, JACKSON, JAVADOC, SPRINGMVC, SWAGGER3, SWAGGER2);
}
```

### 2.3 校验器行为

```
读 plugin.mcp.parser.des   （缺省 → 不校验，用默认集合）
读 plugin.mcp.parser.param （缺省 → 不校验，用默认集合）
  ↓
逐名比对（大小写不敏感，与 ParserCondition 的 equalsIgnoreCase 保持一致）
  ↓
未知名 → 收集
  ↓
plugin.mcp.parser.strict = true ?
  ├─ 是 → 抛 IllegalStateException（带完整未知名清单 + 合法名清单），拒绝启动
  └─ 否 → WARN 日志（列出未知名 + 合法名 + 建议），继续启动
```

**兼容性论证**：默认 `strict=false` → 现有用户行为**逐字节等价**（仅多一行 WARN，且仅在真拼错时才出现）。`strict=true` 是新增的显式 opt-in。

### 2.5 注册纪律合规性自检

| 规范条目 | 本方案如何满足 |
|---|---|
| R1 单一权威源 | 已知名只存在于 `ParserNames` 一处；注解与校验集合不再各写一份 |
| R2 启动断言 | 校验器为 `ApplicationRunner`，容器 refresh 完成后立即执行，**不依赖条件是否被求值** |
| R5 自动发现 | 未新增散落 `if/switch` 判类型分支；仍走 `@ConditionalOnParser` 责任链 |
| 利器 A（注册面与暴露面同源） | 校验的正是"声明面 vs 配置面"，与本框架「注册即暴露」的核心哲学同构 |
| 依赖流向 | 新增类全在 `autoconfigure` 模块，只引 `core` → `common ← core ← autoconfigure ← starters` 不变 |

## 三、风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| `ParserNames` 与实际 Bean 声明漂移（新增解析器时忘记加常量） | 中 | 新解析器被误报为"未知名" | 配套单测：反射扫描 `McpConfig` 中全部 `@ConditionalOnParser` 注解，与 `ParserNames.DES_NAMES/PARAM_NAMES` 双向比对，不一致则**测试失败** → 门禁化 |
| 用户既有配置本就拼错，升级后突然刷 WARN | 中 | 日志噪音（不影响功能） | 默认只 WARN 不阻断；WARN 文案直接给出合法名清单，可自助修复 |
| `strict=true` 用户启动被拒 | 低 | 该用户需改配置 | `strict` 是新增的 opt-in 开关，默认 false，现有用户不受影响 |

**回滚成本**：纯新增 + 等价替换，`git revert` 单 commit 即可，零数据迁移、零 API 破坏。

## 五、实施结果（2026-10-28 · 董事长批准后开工）

### 5.1 与原方案的差异（实施中优化）

| 项 | 原方案 | 实际实施 | 理由 |
|---|---|---|---|
| 已知名权威源 | `ParserNames` 常量类持有两个 `Set` | **权威改为 `PluginProperties.DesParserType` / `ParamParserType` 两个枚举**，`ParserNames` 是其在注解侧的镜像 | 实施时发现这两个枚举**本就存在**且是配置契约的一部分；`@ConditionalOnParser` 的 value 必须是编译期常量（`Enum.name()` 不满足），故仍需常量层，但权威应归枚举 |
| 校验器读配置 | 直接读 `Environment` 原始字符串 | 同左 | `PluginProperties` 从未被 `@EnableConfigurationProperties` 引用（其包不在用户组件扫描路径内），枚举强校验**从未生效**；`Conditions.ParserCondition` 也是直接读 `String[]` |
| 匹配大小写 | 不敏感 | 不敏感 | 与 `Conditions.ParserCondition` 的 `equalsIgnoreCase` 保持一致，避免「校验器说不合法但条件判定能命中」的矛盾 |
