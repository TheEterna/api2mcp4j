## 一、MySQL 资产归属判定（2026-10-27 实测）

### 1.1 判定方法与安全边界

**只做被动侦察 + 一次凭据可达性测试**。全程遵守：

- 仅针对已审计确认的自有资产 `[REDACTED-MYSQL-HOST]`
- 仅试**唯一泄漏的那组**凭据（`root` + 已泄漏密码），**不做任何字典爆破**（本仓 `brute_mysql.py` 的爆破能力**未用于本次判定**，且该脚本已从仓库移除）
- **不尝试 SSH 登录** —— 一旦机器归属变更，登录即构成未授权访问

### 1.2 端口状态对比（08-05 审计基线 vs 今日）

| 端口 | 2026-08-05 | 2026-10-27 | 解读 |
|---|---|---|---|
| 22 SSH | closed | **OPEN**（`OpenSSH_9.3`） | 有活跃系统 |
| **3306 MySQL** | closed (RST) | **FILTERED（timeout/DROP）** | 防火墙**专门 DROP** 3306 |
| 33060 / 3307-3309 | — | FILTERED (DROP) | 同上 |
| 6379 Redis | 未测 | **OPEN** | 跑着服务 |
| 5432 PostgreSQL | 未测 | **OPEN** | 跑着服务 |
| 8888 | closed | **OPEN**（HTTP `502 Bad Gateway`） | 有反向代理、后端已挂 |
| 80 / 443 | closed | CLOSED (RST) | — |
| ping | 通（延迟抖动） | 通（10-12ms） | 在线 |
| 反向 DNS | NXDOMAIN | NXDOMAIN | 云厂商停机/新实例均无 PTR |
| ipinfo 归属 | 腾讯云北京 AS45090 | 腾讯云北京 AS45090（**未变**） | 同运营商 IP 池 |

### 1.3 判定

**08-05 的基线特征是「全端口关闭的停机实例」；今日是「同时跑 Redis + PostgreSQL + SSH 的通用云主机」—— 判若两机。**

且 3306 从 `closed(RST)` 变为 `FILTERED(DROP)`：**RST 意味着无服务在监听，DROP 意味着有防火墙规则在丢弃**。一台到期停机的机器不会有专门针对 3306 的 DROP 规则。

**结论：原 MySQL 实例已被腾讯云释放，IP 资源池回收后重分配给新用户，新用户运行着 Redis + PostgreSQL + SSH。**

### 1.4 因此「改密码」的三层处置

| 层 | 动作 | 状态 |
|---|---|---|
| L1 实例层 | 登录 MySQL 改密码 | ❌ **不可能** —— 无 MySQL 实例；且机器已属他人，**不得尝试** |
| L2 凭据流通层 | **销毁凭据的公开路径**（git 历史） | ✅ **已完成**（见第二节） |
| L3 复用层 | 排查 `[REDACTED-MYSQL-PASSWORD]` 是否在**其它系统**复用（邮箱 / 其它服务器 / 其它数据库） | 🔴 **需董事长在腾讯云控制台 + 其它系统自查**（AI 无法访问） |

> **L3 是当前最大的残余风险**：该密码在 2025-07-08（localhost 版）到 2025-10-22（公网版）两个 commit 中都是同一个值，审计已判定「同一作者沿用至今」。若它在董事长的个人邮箱或另一台服务器上复用，则爆破面与本次 MySQL 无关地继续存在。

### 1.5 攻破与否的诚实结论

| 时间 | 事件 | 风险 |
|---|---|---|
| 2025-07-08 | 凭据（localhost + 弱密码）进入 git | — |
| 2025-10-22 | 凭据升级为**公网 IP** 版本进入 git | 🔴 凭据公开可查 |
| 2025-10-22 → 实例停机 | **≥ 9 个月**公网暴露窗口，弱密码 + `root` | 🔴🔴 自动扫描几乎必中 |
| 2026-08-05 | 审计发现，端口已全关 | 疑似已停机 |
| 2026-10-27 | 端口状态显示为**他人**机器 | 原机已销毁，**证据不可查** |

**无法证伪 → 按「已攻破」处置**。具体含义：

1. 假定 `yizi` 库的数据**可能已被读取/篡改/删除** → 若其中含用户数据，应按数据泄露事件评估合规义务
2. 假定 `root` 账户可能已被创建后门账号 → 云主机建议**整体销毁重建**（而非只改密码），因为无法审计一个已被攻破的系统的完整性
3. 假定该弱密码在其它系统的复用账户**可能已失守** → L3 排查

### 2.4 强制推送与远端实证

**推送前发现的重要事实**：GitHub 远端 master 一直停在 `0ed3b24`（本地大量提交**从未推送**），而 `0ed3b24` **正含**泄漏的 IP 与真实邮箱 —— 即 GitHub 此刻公开着凭据。**这使强制推送从「可选」变成「必须」**。

```
git push --force --mirror origin
→ + 0ed3b24...e4e3310 master -> master (forced update)
→ + 2315b87...7be341f v0.0.1-Basic-Function-Integration (forced update)
→ + 5571717...7f29f9f v1.0.1 (forced update)
→ * [new branch] feat/mcp-protocol-integration
```

### 2.5 副作用与不可逆点

| 影响 | 说明 |
|---|---|
| **所有 commit hash 变更** | 旧 hash 全部失效；`git log` 中的 `9c8be8b` / `687f19d` 等引用已成历史名词 |
| **协作者需重新 clone** | 本机 `~/api2mcp4j-backup-20261027-162447/` 保留完整旧历史，可按需还原 |
| **已 fork 的副本仍含旧历史** | filter-repo 无法触及他人 fork —— **需在 GitHub 设置里逐一核查并联系** |
| **GitHub 会因强制更新回收旧 ref 的可达性** | 悬空对象由 GitHub 后台 GC 清理（通常数天至数周），期间旧对象可能仍可经已知旧 hash 直取 |
| **备份 bundle 本身就是敏感资产** | 含旧凭据，**不可上传任何共享位置**；`~/` 下 600 权限自留 |
